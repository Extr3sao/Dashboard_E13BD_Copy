# E13DB technical debt register (review 001–011)

Priorities use operational/product impact, not arbitrary numeric scores.

| ID | Priority | Area | Problem / evidence | Impact and recommendation |
|---|---|---|---|---|
| TD-001 | P1 | Audit→Finding integration | `/api/audit/post-crq/run` calls `finding_store.reconcile_post_crq` in `src/api/main.py`; `AutomationService.execute_job/_execute_job_thread` does not reference `FindingStore` or `reconcile_post_crq`. CPD browser fixture manually inserts this hook in `scripts/cpd_fixture_server.py`. | Scheduled runs can update `job_runs`/automation facts while Findings, red flags, Fleet and investigations remain stale. E13DB-012: one canonical reconciliation service and identical manual/scheduled receipt tests. |
| TD-002 | P1 | SMTP side effects | `AlertingService._deliver` sends SMTP before transaction commit persists `alert_deliveries` / `notification_count` (`src/api/alerting_engine.py`). | Crash-after-SMTP-accept may cause duplicate messages or lose authoritative delivery status. Add durable outbox/attempt identity and UNKNOWN reconciliation; use provider idempotency when available. Do not promise exactly-once. |
| TD-003 | P1 | Audit idempotency | `reconcile_post_crq` calls `reconcile` without forwarding a stable AuditRun ID; `reconcile` creates a random UUID by default. Successful receipts are per run. Non-success audits do not record reconciliation receipts. | Replaying a request can inflate occurrence/Red Flag counts; repeated failed runs can increment health counters. Use caller-generated stable execution identity and a failure receipt, with replay semantics tested. |
| TD-004 | P1 | Rule/capability provenance | `RuleDefinition` supports engine/version/privilege/license/capability metadata (`check_engine.py`) but the production legacy Post-CRQ route is not uniformly routed through it; audit rows lack immutable rule-pack and effective capability snapshot. | A historical “not found” cannot distinguish absent condition from a rule that was skipped/unavailable or later changed. Bind per-rule version and capability/privilege/license snapshot to AuditRun/RuleResult before adding deeper diagnostics. |
| TD-005 | P2 | Multi-store transaction boundary | Findings/alerts/investigations live in `internal_db`; scheduled jobs/facts/retries in `automation.db`; report/export artifacts live on filesystem. | No cross-store atomic commit or common recovery transaction. Keep stores separated if useful, but add one stable operation ID and reconciliation receipt across boundaries; document partial cut points. |
| TD-006 | P2 | Migration ledger | Store constructors perform additive schema creation/column checks. No central ordered schema migration ledger for both databases; CPD backup compatibility has a manual version/signature. | Upgrade/rollback evidence is harder to reproduce; additive-only changes need disciplined compatibility tests. Introduce explicit ordered schema versions before a breaking migration. |
| TD-007 | P2 | Channel circuit breaker | SMTP failures are stored and health degrades; cooldown/dedupe is per alert/report, not a global channel breaker. | Many distinct P1 alerts can still each attempt a failing SMTP connection. Add a bounded global channel cooldown/probe and a clear recovery event; preserve per-alert receipts. |
| TD-008 | P2 | Investigation evidence retention | `investigation_evidence` duplicates normalized occurrence summaries per case and has no investigation-specific retention. | Ongoing/recurring cases can grow data. Add bounded policy that preserves open cases, operator causes and resolution history; measure before purging closed case evidence. |
| TD-009 | P2 | Investigation lineage | Evidence stores Finding/occurrence/run IDs, but no rule version, producer/runtime SHA or capability snapshot. Investigation hypothesis refresh updates derived rows in place. | The DBA cannot reproduce precisely which rule/capability produced older evidence. Add source identity and immutable derivation receipts; do not overwrite operator decisions. |
| TD-010 | P2 | Runtime/audit identity | Operations summary has operational state but no compact application SHA/schema/rule-pack/config fingerprint manifest. | Incident comparison and historical AuditRun reproduction require external Git/log lookup. Add secret-free runtime and per-AuditRun manifests. |
| TD-011 | P2 | Request-path scaling | Synthetic scale receipt shows Fleet at ~1.52 s / 100 targets and 73k audit rows on this Windows/SQLite host; list N+1s were reduced in this review. | Fleet remains the largest measured screen/query surface; profile realistic indexes/query plan before further growth. No production SLO is inferred from the synthetic host. |
| TD-012 | P2 | Main composition root | `src/api/main.py` ~2.8k LOC; automation service/store ~2.2k/~2.7k LOC and combine multiple responsibilities. | Adds onboarding/change risk and encourages duplicate routes. Extract only when E13DB-012 introduces concrete audit/capability boundaries; no rewrite now. |
| TD-013 | P2 | Failure taxonomy | `RuleEngine` has PASS/WARN/FAIL/ERROR/SKIPPED but timeout/provider details often collapse into ERROR/string; delivery has a richer taxonomy. | Operators cannot reliably distinguish timeout, unreachable, auth, privilege, license, storage lock and internal errors. Normalize at adapter boundaries with retryability and evidence. |
| TD-014 | P3 | Timestamp conventions | Finding/audit/alert timestamps use epoch floats; job history uses UTC strings; some legacy inputs are local-time parsed. | Cross-domain joins and operator display can be timezone-sensitive. Standardize new durable contracts to UTC epoch/ISO with explicit zone and retain migration compatibility. |
| TD-015 | P3 | Dead fallback helpers | `InternalDBManager` / `AutomationStore` still have fallback path builder methods though startup now fails closed. | Confusing dead code. Remove during a targeted storage maintenance change after confirming no external callers. |
